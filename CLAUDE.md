## What this repo is

Public, opinionated Claude Code defaults for Node.js / TypeScript projects. It ships subagents, user-invocable slash commands, a permissions baseline, and a CLAUDE.md template that users drop into consumer projects. No application code, no build, no test suite. Work here is editing markdown and JSON under `.claude/` plus the top-level `README.md`.

## Layout

- `.claude/claude-defaults.md` — behavioural defaults (planning, thinking, subagents, verification) that consumer projects pull into their own `CLAUDE.md` via `@.claude/claude-defaults.md`. Edit this to change the per-session rules everywhere at once. Keep it under ~20 lines — it's re-sent every turn in every consumer project. Don't restate guidance that already lives in Claude Code's built-in system prompt.
- `.claude/MEMORY.md` — project conventions Claude should know about, currently a slash-command natural-language trigger table. Optional `@.claude/MEMORY.md` import from a consumer's `CLAUDE.md`; not auto-loaded otherwise.
- `.claude/agents/` — subagent definitions (frontmatter: `name`, `description`, optional `model`, `isolation`).
- `.claude/commands/` — slash commands triggered by `/<name>`. Filename = command name. No frontmatter. Use `$ARGUMENTS` for user-supplied args. **Never put a `README.md` in here** — Claude Code would register it as `/README`.
- `.claude/skills/` — auto-invocable capabilities (one subdirectory per skill, each with a `SKILL.md` carrying YAML frontmatter). Ships `test-locators` (proactive frontend test-attribute guidance); see `.claude/skills/README.md` for the convention.
- `.claude/settings.json` — checked-in, team-shared permissions baseline, the small set of universally-safe hooks that no-op when not applicable, and the default `enabledPlugins`. Conventions: `.claude/rules/settings-and-permissions.md`.
- `.claude/settings.local.json` — per-machine overrides, gitignored.
- `.claude/settings.plugins.example.json` — opt-in MCP-backed plugins (github, linear, context7), for users to copy from.
- `.claude/settings.codex.example.json` — opt-in Codex failover (OpenAI's `codex-plugin-cc`); a third-party marketplace, so deliberately not in the baseline. **Keep it modular** — all Codex content stays in this file plus bounded doc sections, never threaded through unrelated machinery, so it stays trivially portable and droppable. Conventions: `.claude/rules/settings-and-permissions.md`.
- `.claude/output-styles/` — opt-in reply formats (one `.md` per style, YAML frontmatter with `name`/`description`). `settings.json` sets `brief.md` ("Brief") as the **default** `outputStyle`, a deliberate owner decision; `{"outputStyle": "Default"}` in `settings.local.json` restores the stock voice without forking the baseline. **Always set `keep-coding-instructions: true`** — the field defaults to `false`, which silently drops Claude Code's built-in engineering instructions. Full conventions, including why `Brief` survives the built-in `Concise` style and the `AWAITING.md` marker discipline that depends on it: `.claude/rules/output-styles.md`.
- `.claude/hooks/` — executable scripts referenced from `settings.json`; `statusline.sh` lives here too. **The status line is where spend gets reported**, which is why `claude-defaults.md` forbids stating cost in prose. Hooks must be self-detecting and exit 0 on every non-applicable input. **Always reference a hook by an absolute, shell-expanded path** — a bare relative `.claude/hooks/…` resolves against the session cwd, so it exits 127 in any project that doesn't itself ship the script and the hook silently never runs. Full conventions: `.claude/rules/hooks-and-scripts.md`.
- `.claude/scripts/` — executable scripts the **user** runs directly, as opposed to `hooks/` (invoked by Claude Code) and `commands/` (invoked as `/name`). Adding anything here needs a matching `!.claude/scripts/` line in the root `.gitignore`. Full conventions: `.claude/rules/hooks-and-scripts.md`.
- `.claude/rules/` — path-scoped instruction files: a `paths:` glob list in YAML frontmatter makes a rule load **only when Claude reads a matching file**, instead of every turn. This is where the per-area conventions relocated out of this file live; the always-loaded headline for each one stays here, because a prohibition has to be in context *before* you consider the change it forbids, and a rule only fires on a **read** — a brand-new file written from scratch matches nothing. Three measured properties worth knowing. (a) A pattern is **only root-anchored if it starts with `/`** — a bare `install.sh` matches that basename in *any* directory (it fired for `ai-bridge/install.sh`), and a trailing globstar is no better: `.claude/hooks/**` also matched `ai-bridge/symlink/.claude/hooks/*`. Write `/install.sh` and `/.claude/hooks/**`. A pattern with a separator and no globstar (`a/b.txt`) *is* anchored, and `./x` matches **nothing at all** — a silently dead rule. **The official docs table is wrong here**, claiming `*.md` matches "Markdown files in the project root" and advising against a leading slash; measured against v2.1.239 with an `InstructionsLoaded` hook, both are false. (b) Globs are matched relative to the project directory and never match a file outside it, so a rule can only ever govern this repo's own files. (c) A rule with no `paths:` — **including one whose frontmatter fails to parse** — loads unconditionally at session start, so a typo costs headroom silently instead of erroring. Absence is safe: delete a rule file and nothing errors, the guidance is just gone. Needs a matching `!.claude/rules/` line in the root `.gitignore`, and `rules` in `install.sh`'s `EXCLUDE` — these are **repo**-specific rules, and symlinking them into `~/.claude/rules/` would silently apply them to every project on the machine.
- `.claude/potential-bugs.md`, `.claude/techdebt.md`, `.claude/plans/` — runtime output of `/scan`, `/techdebt`, `/plan`. Auto-created in target projects on first run, gitignored, never seeded in this repo. The `/plan` slug is the Jira key when detected on branch / recent commits, else a kebab-case verb-prefixed summary (`feat-…`, `fix-…`, `chore-…`); plan files ride with the related PR(s) and are deleted once the work merges to main.
- `.claude/README.md` — human inventory + commands-vs-skills note. Must stay in sync with the top-level `README.md` when agents/commands change.
- `README.md` (root) — public-facing setup guide.
- `docs/instruction-surface-inventory.md` (root) — the classification of every always-loaded rule in this repo's root `CLAUDE.md` and in `ai-bridge/seed/CLAUDE.md` (ALWAYS / PATH-CORRELATED / PROCEDURAL / DERIVABLE), plus the measured limits of `paths:`-scoped rules. **Read it before moving a rule between `CLAUDE.md` and `.claude/rules/`** — it records what was deliberately left always-loaded and why, so the same ground isn't re-argued. Update it when you move one.
- `.coderabbit.yaml` (root) — CodeRabbit review config **for this repo only** (not shipped to consumers; `install.sh` is scoped to `.claude`). Enforces **one review per PR**. Conventions: `.claude/rules/repo-config.md`.
- `install.sh` (root) — user-wide installer. Per-entry symlinks the tracked `.claude/` defaults **into** `"${CLAUDE_CONFIG_DIR:-$HOME/.claude}"` (never a whole-dir symlink, so runtime state stays out of the repo). Auto-discovers what to link via `git ls-files .claude`, minus a small `EXCLUDE` denylist. Idempotent; backs up anything it would overwrite. **`ADOPTABLE_KEYS` / `adopt_keys()` is the one place the installer edits a user's real file, and it must stay display-only.** Full conventions: `.claude/rules/repo-config.md`.
- `ai-bridge/` (root) — a **reusable OKF control-panel template** (a separate subtree, not part of the `~/.claude` config layer). `symlink/` holds generic machinery symlinked into per-group **instances**; `seed/` holds starting content copied once; `install.sh` stamps out / refreshes an instance. Keep machinery generic — org/repo/path/team/channel literals live in an instance's `instance.config.json` / `CLAUDE.md`, never in `symlink/`. The root `install.sh` is scoped to `.claude` and never touches this subtree. Full layout and its load-bearing invariants: `.claude/rules/ai-bridge.md`.

## Commands vs skills

This repo ships mostly **commands** (`.claude/commands/<name>.md`, invoked only when the user types `/<name>`). Skills (`.claude/skills/<name>/SKILL.md`) auto-invoke via intent matching. When asked to add a capability, default to a command unless proactive invocation is explicitly wanted — `test-locators` is the one skill so far, because adding test attributes should happen automatically while building frontend, not on a typed command. See `.claude/README.md` for the full distinction.

## Conventions when editing

- **Agents must stay generic.** No references to specific projects, codebases, or internal helpers. Agents should infer the toolchain from `package.json` scripts and whatever `CLAUDE.md` the consumer project ships.
- **Commands must stay generic too.** Same rule — no project-specific paths, no internal tooling. Commands ship to consumers.
- **Inventory lives in three places, with different jobs.** Agent `description:` frontmatter is the dispatch trigger Claude Code matches on — keep it terse and action-shaped. The "Purpose" columns in `.claude/README.md` and the top-level `README.md` are human-readable and may be more verbose. They need not be word-for-word identical, but none of the three may drift from what the agent actually does. When you add, remove, rename, or materially change an agent, command, or skill, walk all three. If `claude-defaults.md` mentions the agent by name, update it there too.
- **The fenced CLAUDE.md template in `README.md` (the "Bootstrap a CLAUDE.md" section) is consumer-facing.** Edit it as boilerplate users paste into their own projects, not as guidance for this repo. Don't expand the example bullets — they're intentionally placeholders.
- **The one MCP-tool permission in the baseline is `mcp__claude-in-chrome__*`, and it's deliberate** — and it is **not** a precedent for other MCP allow rules: the justification is that it's inert until the consumer installs and pairs the Chrome extension, not convenience. Full rationale, scope, and the way back: `.claude/rules/settings-and-permissions.md`.
- **`settings.json` is the checked-in, team-shared baseline.** Permissions live here; MCP servers and env vars do not. Hooks may ship here, but only if **universally safe** — they must no-op cleanly when the project doesn't match. Per-machine additions go in `.claude/settings.local.json` (gitignored). Details: `.claude/rules/settings-and-permissions.md`.
- **Default plugins (`enabledPlugins`) live in `settings.json`; MCP-backed plugins do not.** Enabling a plugin also enables **its hooks** — check them before defaulting anything on. Details: `.claude/rules/settings-and-permissions.md`.
- **The DeepSeek backend is a launcher, not a settings file — don't "harmonise" it.** **Keep it opt-in and easy to leave out entirely** — routing a whole session to a third party is unacceptable under many organisations' data-governance rules, so any setup with such constraints should be able to simply not have these files. Full rules, including the two safety properties to preserve if you edit it: `.claude/rules/hooks-and-scripts.md`.
- **`ai-bridge/` carries load-bearing invariants — **a count is deliberately not given here**, because it drifted twice in one day (a bullet added without bumping the number, in both directions) — read `.claude/rules/ai-bridge.md` before editing anything under it.** Headlines, in the order they appear there: `AWAITING.md` is the only status artifact and is **opt-in by presence** (there is deliberately no `/status` command — don't reintroduce one); a capability some deployments must not have is **one deletable file**, not a flag threaded through the machinery, and **absence must mean the safe behaviour, never an error**; `build` and `research` projects are **deliberately asymmetric** — don't restore a question for symmetry; the delegated merge gate resolves its required checks in `required-checks.sh` and **exit 0 is the only clearance**; `prune-worktrees.sh` is **report-only** — do not reintroduce a delete, not even behind a flag; `validate-bundle.sh` was **scoped by measuring first**, and validates only the schema-defined locations; `migrate-bundle.sh` **fixes only what has one right answer**, is report-only by default, and a **false success is worse than the error it claims to fix**; and the scaffold review is a **three-stage chain with a declared fallback, never a skip**.
- **Permission patterns: prefer the simple shapes.** `Bash(cmd:*)` (trailing wildcard) and exact-string matches are reliable; mid-pattern wildcards are fragile, so don't ship them as deny rules. If you need argument-level filtering, use a `PreToolUse` hook. Details: `.claude/rules/settings-and-permissions.md`.
- **Don't ship deny rules that block harmless files.** Block real env files (`.env`, `.env.local`, `.env.*.local`) and private keys (`id_rsa`, `id_ed25519`, `id_ecdsa`), not `.env.example` or `*.pub`. Details: `.claude/rules/settings-and-permissions.md`.
- **Opus 4.8 is the target.** Guidance in agents and the CLAUDE.md template assumes 4.8 behavior (adaptive thinking, explicit subagent spawning, xhigh default). Don't rewrite for older models (4.6/4.7).
- **Don't invent tool invocations.** If a command references `gh stack`, `coderabbit`, etc., check the actual command surface before committing — users run these verbatim.
- **Addressing review feedback: fix, push, reply once — never ask for a re-review.** CodeRabbit is configured for a single review per PR (`.coderabbit.yaml`). Verify your own fixes; only a rewrite that invalidates the original review justifies an explicit `@coderabbitai review`.
- **After adding/moving commands or agents, restart Claude Code and verify registration** — `/exit`, then `claude`. New files aren't picked up mid-session.
- **Don't rename or move `.claude/claude-defaults.md`.** Consumer projects pin it as `@.claude/claude-defaults.md` in their own CLAUDE.md; renaming or relocating it silently breaks every downstream setup that pulled from this repo.

## Verifying a change

No build, lint, or test suite — markdown + JSON only. The verification loop is:

1. `/exit` and relaunch `claude` so the session re-scans `.claude/agents/` and `.claude/commands/`.
2. Invoke the changed command (`/<name>`) or ask Claude to use the changed agent; confirm it registers without a `skills:` prefix and behaves as intended.
3. For `settings.json` edits, trigger an affected tool call and confirm the expected allow/deny/prompt outcome.
4. For a `.claude/rules/` edit, confirm the rule actually fires: register an `InstructionsLoaded` hook, read a file its `paths:` glob should match, and check the hook logged that rule with `"load_reason":"path_glob_match"`. `/context` shows what loaded at session start. Don't infer it from the frontmatter — a `paths:` list that fails to parse loads the rule unconditionally instead of erroring, which looks identical from the file.

## Out of scope

- Don't add CI, GitHub Actions, or a build step — this is a config-only repo.
- Don't add a `package.json` unless you have a reason tied to tooling for editing markdown.
